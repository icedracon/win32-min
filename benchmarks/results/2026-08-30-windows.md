# Windows binding comparison — 2026-08-30

This is a reproducible baseline for one deliberately small operation: compile
a program that obtains the current Windows process ID. It measures the
cost of the selected package surfaces on one machine; it is not a universal
speed or quality ranking.

| Metric | `win32-min` 0.1.3 | `windows-sys` 0.61.2 | `windows` 0.62.2 |
| --- | ---: | ---: | ---: |
| Clean-target build, mean ± sample stddev | 0.400 ± 0.033 s | 0.732 ± 0.028 s | 5.049 ± 0.668 s |
| Application-only rebuild | 0.199 s | 0.198 s | 0.220 s |
| `cargo doc --no-deps` | 0.409 s | 0.769 s | 1.969 s |
| Release executable | 130,560 B | 130,560 B | 130,560 B |
| Resolved packages, excluding benchmark app | 1 | 2 | 15 |
| Binding crate Rust source | 37 files / 197,567 B | 249 files / 18,144,057 B | 693 files / 114,131,735 B |

On this workload and host, `win32-min`'s mean clean-target build was 1.83×
faster than `windows-sys` and 12.62× faster than `windows`. The
application-only rebuilds and final executable sizes were effectively the same.
The larger Microsoft crates provide substantially broader generated API
coverage, so these results support a narrow-cost claim, not a general
replacement claim.

## Method

- Five clean-target observations per variant, with build order rotated each
  run to balance first/last position.
- Registry sources prefetched before timing; every resolved package pinned by
  the committed lockfiles.
- Each benchmark has an independent target directory. Clean-target builds
  remove that directory, but retain downloaded sources and operating-system
  file caches.
- The incremental measurement touches only the tiny benchmark application's
  source timestamp, rebuilds it with dependencies cached, then restores the
  timestamp.
- All three release programs perform the same `GetCurrentProcessId` operation.

Environment: Intel Core Ultra 7 255HX; Microsoft Windows 10.0.26200; Rust
1.94.1; Cargo 1.94.1. Run timestamp: 2026-08-29 21:28:51 UTC.
